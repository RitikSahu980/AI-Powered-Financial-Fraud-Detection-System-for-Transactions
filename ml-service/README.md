# Fraud Detection ML Service

Thin FastAPI microservice that wraps a saved `scikit-learn` pipeline
(`ColumnTransformer` + `OneHotEncoder` + `XGBClassifier`) and exposes fraud
prediction over HTTP.

This service implements **exactly** the frozen technical contract's ML
Input/Output Contract. It contains **no business logic**: no confidence
calculation, no risk thresholds, no alert creation, no authentication, no
database access. Those responsibilities belong to the Spring Boot backend
that calls this service.

## Architecture position

```
React → Node.js API Gateway → Spring Boot → [this service] → Spring Boot → MongoDB → Node.js → React
```

Only Spring Boot calls this service. It should not be reachable directly
from the frontend, the API gateway, or the public internet.

## What this service does, step by step

1. Accepts a raw transaction (`POST /predict`).
2. Computes two engineered features server-side:
   - `origBalanceDiff = oldbalanceOrg - amount - newbalanceOrig`
   - `destBalanceDiff = oldbalanceDest + amount - newbalanceDest`
3. Assembles a 9-column pandas DataFrame in the exact order the pipeline
   was fit on: `step, type, amount, oldbalanceOrg, newbalanceOrig, oldbalanceDest, newbalanceDest, origBalanceDiff, destBalanceDiff`.
4. Calls `pipeline.predict()` and `pipeline.predict_proba()` on the
   already-loaded pipeline (loaded once at startup, never per-request).
5. Returns `{prediction, fraud_probability, model_version}` — nothing else.

## Running locally (without Docker)

Requires Python 3.11.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env               # adjust if needed - defaults work out of the box

# Place online_payment_fraud_detection_model.pkl in this directory
# (same level as requirements.txt) before starting the service.

uvicorn app.main:app --reload --host 0.0.0.0 --port 8000
```

If the model fails to load or fails structural verification, **the service
will refuse to start** and will log exactly which check failed. This is
intentional — see "Startup verification" below.

## Running with Docker

```bash
docker compose up --build
```

The model artifact `online_payment_fraud_detection_model.pkl` must exist in
this directory before building the image — it is copied into the image at
build time (see `Dockerfile`).

## API

### `GET /health`

```json
{
  "status": "ok",
  "model_loaded": true,
  "model_version": "xgboost_v1"
}
```

### `POST /predict`

Request:
```json
{
  "step": 1,
  "type": "TRANSFER",
  "amount": 181,
  "oldbalanceOrg": 181,
  "newbalanceOrig": 0,
  "oldbalanceDest": 0,
  "newbalanceDest": 0
}
```

`type` must be one of: `CASH_IN`, `CASH_OUT`, `DEBIT`, `PAYMENT`, `TRANSFER`
(verified against the loaded model's encoder at startup — see "Startup
verification"). Any other value, or any missing/negative/non-finite
numeric field, is rejected with a `422`.

Response:
```json
{
  "prediction": 1,
  "fraud_probability": 0.999934,
  "model_version": "xgboost_v1"
}
```

`prediction`: `0` = Not Fraudulent, `1` = Fraudulent — raw model output.
`fraud_probability`: raw model output, full precision, not rounded.
This service intentionally does **not** return `confidence` or
`risk_level` — those are computed by Spring Boot.

Interactive API docs (Swagger UI) are available at `/docs` when the
service is running.

## Startup verification (Step 5a)

On every startup, before accepting any traffic, this service:

1. Loads the pipeline via `joblib.load(MODEL_PATH)`.
2. Verifies it is a `sklearn.pipeline.Pipeline` with `preprocessor` and
   `classifier` steps.
3. Verifies the preprocessor is a fitted `ColumnTransformer` containing a
   `cat` transformer that is a fitted `OneHotEncoder`.
4. Verifies the encoder's categories exactly match
   `{CASH_IN, CASH_OUT, DEBIT, PAYMENT, TRANSFER}` — the same set the
   `TransactionRequest` schema accepts. A mismatch here means the API
   schema and the deployed model are out of sync, and the service refuses
   to start rather than silently misclassify unrecognized categories.
5. Verifies the pipeline's expected input columns
   (`feature_names_in_`) exactly match this service's
   `MODEL_FEATURE_COLUMNS` constant, in order.
6. Verifies the classifier exposes `predict()` and `predict_proba()`.

If any check fails, the service logs exactly which one and refuses to
start. See `app/services/predictor.py::_verify_pipeline_structure`.

## Testing

```bash
pytest
```

Requires `xgboost` installed (see `requirements.txt`) and
`online_payment_fraud_detection_model.pkl` present in the project root,
since most tests run against the real loaded pipeline rather than a mock —
this is deliberate, since the thing most worth testing is that the running
service reproduces the training notebook's own outputs.

`tests/test_structural_verification.py` is the exception: it constructs
minimal `scikit-learn` pipelines directly and does not require `xgboost`
or the real artifact, so it can run in more constrained environments.

### Generating the permanent regression fixture

Run once, against the real loaded pipeline, before running the test suite
for the first time (and again any time the model artifact changes):

```bash
python scripts/capture_smoke_tests.py
```

This loads `online_payment_fraud_detection_model.pkl` (running full Step 5a
structural verification as it does), runs a set of representative
transactions through it, and writes the real `prediction` /
`fraud_probability` pairs to `tests/fixtures/smoke_test_transactions.json`.
`tests/test_predict.py` then asserts the running service reproduces those
exact values on every test run.

This exists specifically to avoid a mistake we already made once during
planning: two probability values were referenced from the training
notebook (`5.469514e-08` and `0.9999666`) whose exact input rows were never
preserved, so they could not be trusted as regression assertions — see the
frozen contract's correction note. Every case in the generated fixture is
input-first: the transaction is defined, then run through the real
pipeline, so the recorded output is guaranteed reproducible.

If `tests/fixtures/smoke_test_transactions.json` is missing,
`test_predict.py`'s fixture-based tests are **skipped with an explicit
message** telling you to run the capture script — never silently treated
as passing.

If any fixture-based test fails after the fixture already exists, **do not
edit the fixture to make it pass.** It means either the deployed model
artifact has changed or the feature engineering has drifted from what the
model expects. Investigate first; if a new model version is the deliberate
cause, re-run the capture script and review the diff before committing it.

## Known environment note from initial development

This project's structural verification (Step 5a) was first performed in a
sandboxed development environment with no outbound access to any package
registry (PyPI, npm, and the Ubuntu package archives were all unreachable
from that sandbox), using a minimal attribute-only stub in place of the
real `xgboost` package — sufficient to inspect the pipeline's structure,
encoder categories, and hyperparameters (all confirmed to match the frozen
contract exactly), but **not** to execute a real `predict()`/
`predict_proba()` call or run the test suite.

**The first real run of this service — and generation of the permanent
regression fixture — must happen in an environment with real internet
access**, following this order:

```bash
cd ml-service
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python scripts/capture_smoke_tests.py   # generates tests/fixtures/smoke_test_transactions.json
pytest                                   # full suite, including fixture-based regression tests
uvicorn app.main:app --reload            # run the service itself
```

If `capture_smoke_tests.py` fails during its Step 5a verification call
(`service.load()`), stop — that means the loaded artifact does not match
what was verified during development, and the mismatch must be resolved
before proceeding to `pytest` or running the service.

## What this service must never contain

Per the frozen technical contract, Part 7:

- Confidence calculation
- Risk level / threshold logic
- Alert creation
- Authentication or authorization
- MongoDB or any persistence logic
- Manual encoding, scaling, or refitting of any kind — all preprocessing
  lives inside the saved pipeline artifact

If a future change seems to require any of the above inside this service,
that is a signal the change belongs in Spring Boot instead, or that the
frozen contract itself needs to be revisited and re-frozen deliberately —
not a reason to add it here quietly.
